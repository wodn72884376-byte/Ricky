## 2. 네비게이션 구조

### 글로벌 헤더 (스토어 전역)

```
좌      BEST   Men's ▾   Women's ▾   Kids ▾   이번 주 입고
중앙                    RICKY
우      주문 내역   장바구니(n)   로그인
```

**메가 드롭다운** — `Men's` / `Women's` / `Kids`에 걸린다. 컬럼은 그 축에 상품이 있는 브랜드만 만든다.

```
Arc'teryx          lululemon          Coach
─────────          ─────────          ─────
전체               전체               전체
아우터             아우터             가방
상의               상의               지갑
하의               하의               신발
악세서리           악세서리           악세서리
```

- **상단 축은 성별·큐레이션, 브랜드는 드롭다운 컬럼이다.** 홈은 브랜드 3분할로 "무엇을 파는가"를,
  내비게이션은 "어떻게 찾는가"를 맡는다. 3브랜드 × 5카테고리 = 최대 15조합인데, 상단에 브랜드만
  늘어놓으면 `코치 가방`까지 두 단계가 더 걸린다.
- **카테고리는 브랜드마다 다르다.** 코치는 가방이 주력이라 `아우터·상의·하의` 대신 `가방·지갑·신발`이다.
  아크테릭스에 `지갑`을 두지 않는 것과 같은 이유다.
- `BEST`는 `products.featured_rank` 수동 큐레이션이다. 주문이 쌓이면 판매량 기준으로 전환한다.
- `unisex` 상품은 `Men's`·`Women's` 양쪽 목록에 모두 나온다.
- **`Kids`는 어른 축과 겹치지 않는다.** `unisex` 상품은 아동 목록에 나오지 않는다 —
  성인 프리 사이즈가 섞이면 부모가 사이즈를 착각한다. 지금은 캐나다구스 아동 라인
  7개(2~7years · 6+years)뿐이라 컬럼이 하나다 (마이그레이션 20260830000014).
- 로고는 중앙 (29cm 방식). 좌우가 같은 `flex-1`이어야 실제로 중앙에 선다.
- 주문 확인은 `주문 내역`(계정 메뉴)뿐이다. 회원 전용이라 계정 아래가 제자리다.
- 모바일: 햄버거 전체화면 시트. 성별 축은 아코디언으로 같은 내용을 편다.
  **시트는 `document.body`로 포털한다** — 헤더가 `z-sticky`로 쌓임 맥락을 만들어서,
  그 안에 두면 `z-sheet`를 줘도 헤더 밖 `z-floating`(문의 버튼)을 못 넘는다.
- 스크롤 시 헤더는 남고 보조 행만 내려놓는다.

## 4. URL 규칙

- 전부 소문자 케밥. 한글 slug를 쓰지 않는다 (인코딩 문제 + 공유 시 깨짐).
- 상품 slug: `arcteryx-beta-lt-jacket-black` — 브랜드-모델-색상. `products.slug` unique.
- 목록 필터는 **URL 검색 파라미터**로 (공유·뒤로가기·SEO):
  `/brands/arcteryx?gender=men&category=outerwear&size=M&duty=free&sort=recent`
  - `gender`는 `men` / `women`. `unisex` 상품은 양쪽 모두에 포함된다 — 파라미터 값으로는 쓰지 않는다.
  - `duty=free` = USD 150 이하만 (브리프 §7). 라벨은 `관세 없이 받을 수 있는 것`이며
    `면세`처럼 단정하지 않는다 — 예상치다.
- 주문번호는 경로에 노출된다 → **추측 불가능해야 한다** (§5-2).

## 5. 이 IA가 드러낸 스키마·정책 갭

구현 전에 메워야 한다. 순서는 심각도순.

> **5-1 ~ 5-5는 해소됐다** — `supabase/migrations/20260826000003_guest_orders_and_support.sql`.
> 검증: `npm run db:check` (마이그레이션 실행) · `npm test` (제약·기본값 12건).

**5-1. 게스트 주문 연락 수단** — 해소
`orders.contact_email` 추가. 회원 주문은 `customers.email`로 대체 가능하므로 nullable로 두되,
회원 전용 전환으로 `customer_id`·`contact_email` 이 **둘 다 not null** 이 됐다. 연락 수단은 계정이 아니라
**주문마다** 확정된다 — 네이버 계정은 이메일을 주지 않을 수 있고, 알림 받을 곳이 계정 이메일과 다를 수도 있다.

**5-2. 추측 불가능한 주문번호** — 해소
`next_order_no()`가 `R<YYMMDD>-<6자>`를 만든다. 문자셋은 Crockford Base32(I·L·O·U 제외 —
손으로 옮겨 적을 때 혼동 방지). 32자이므로 `gen_random_bytes` 모듈로 편향이 없고, 하루 32⁶ ≈ 10.7억
공간이다. 충돌 시 최대 10회 재시도해 unique 제약에 걸려 INSERT가 실패하지 않는다.

비회원 조회 경로가 사라져 열거 공격 표면도 함께 사라졌다(`order_lookup_attempts` 삭제).
**주문번호의 난수성은 그대로 둔다** — 주문번호는 메일과 택배 송장에 찍혀 밖으로 나가므로
순차값이면 안 된다.

**5-3. 문의 저장소** — 해소
`inquiries` + `inquiry_replies`. 접수번호 `Q<YYMMDD>-<5자>`도 같은 난수 방식이다.
**회원 전용이다** — `customer_id` not null, insert 정책이 `customer_id = auth.uid()` 를 요구한다.
답변을 어디로 보낼지와 지난 문의를 어디에 쌓을지가 계정 없이는 정해지지 않는다.

**5-4. 찜 · 재입고 알림** — 해소
`wishlists` · `restock_alerts` 모두 회원 전용이다. 중복 방지 키는 `(variant_id, customer_id)` —
이메일이 없는 회원이 생기므로 이메일은 더 이상 신원이 될 수 없다.
`notified_at is null` 부분 인덱스로 발송 대상을 뽑는다.

**5-5. 검수 사진 · 후기** — 해소
`inspection_photos`는 `is_public` 기본값이 **false**다. 영수증·인보이스는 금액·개인정보 마스킹을
확인한 뒤에만 공개한다. `reviews.order_item_id`는 not null + unique이므로
**구매 확인된 후기만, 항목당 하나만** 존재한다.

**5-6. 장바구니 저장 방식 미결**
로그인 전에도 담을 수 있어야 하므로 `localStorage`가 출발점이다 — 주문은 회원 전용이지만
담는 것까지 막으면 로그인할 이유를 보기 전에 벽을 세우는 셈이다. 로그인 시 병합 규칙을 정해야 한다.
**가격은 장바구니에 저장하지 않고 항상 `store_variants`에서 다시 읽는다** — 오래된 가격으로
결제되면 마진이 깨진다.

**5-7. 통신판매업 신고 — 미신고 상태 (2026-08-26 확인)**
국내 통신판매업 신고를 하지 않았다. 이건 디자인이 아니라 사실이므로, **없는 번호를 푸터에
적을 수 없다.** 당장의 처리와 남은 확인 사항을 분리한다.

- **지금 푸터에 쓸 수 있는 것:** 캐나다 사업자명, 알버타 사업자 등록 정보, 소재지, 대표자,
  연락처(이메일 + 문의 채널). 판매자가 누구인지는 명확히 밝힌다.
- **쓰면 안 되는 것:** 통신판매업 신고번호 자리를 비워두거나 `준비 중`으로 채우는 것.
  아예 항목을 만들지 않는다.
- **남은 확인:** 해외 사업자가 한국 소비자를 대상으로 계속 판매할 때 국내 전자상거래법상
  신고·표시 의무가 어디까지 적용되는지. 법무 확인이 필요하며, 결과에 따라 푸터와
  `/policy/terms`가 바뀐다. 오픈 전 마감 항목으로 둔다.

## 6. 빌드 순서 제안

| 순서 | 대상 | 이유 |
|---|---|---|
| 1 | `/admin/products` + `/admin/inventory` | 물건이 없으면 스토어에 보여줄 게 없다 |
| 2 | `/` + `/brands/[slug]` | 브리프가 이미 나와 있다 |
| 3 | `/products/[slug]` | PDP 템플릿이 이미 나와 있다 |
| 4 | 스키마 갭 5-1 ~ 5-4 | 체크아웃 전에 메워야 한다 |
| 5 | `/cart` → `/checkout` → `/orders/*` | 실패 비용이 가장 큰 구간 |
| 6 | `/guide/*` + `/policy/*` | 오픈 전 필수. 분량은 많지만 정적이다 |
| 7 | `/admin/monitoring` | P4. 주문매입 판매를 열기 전에 필요 |
